# 数字原生 PDF 重建流程规范

## 适用判定

本流程适用于由排版软件生成、具有可可靠提取文字对象和字符映射的数字原生 PDF。

下列文件不按数字原生 PDF 处理：

* 扫描后附加 OCR 文字层的 PDF；
* 字符映射大量错误的 PDF；
* 文字对象严重缺失或错序的 PDF；
* 无法根据页面对象可靠恢复阅读顺序的 PDF。

以上情况使用 [`SCAN_DIGITIZATION_WORKFLOW.md`](SCAN_DIGITIZATION_WORKFLOW.md)。

## 输入与产出

输入是数字原生 PDF 的文字对象。产出是从中恢复的**正确文字、阅读顺序和语义结构**，形成可阅读、
可检索、可引用并经人工核验的 Markdown，连同正文所需图片和作品元数据。

章节单元、语义块、block-id、翻译分组、批次、`index.json` 与 `status.json` 在后续预处理阶段建立，
翻译在翻译流程中执行。

正文达到 `human_verified` 后按作品类型分流：

* 书籍进入 [`BOOK_PREPROCESSING.md`](BOOK_PREPROCESSING.md)；
* 单篇文章直接进入 [`ARTICLE_TRANSLATION_WORKFLOW.md`](../translation/ARTICLE_TRANSLATION_WORKFLOW.md)。

Owner 明确授权在底本尚未完成全文数字化核验时翻译指定范围的，按对应翻译流程执行，并保留真实数字化状态、记录未核验风险。先行翻译不代替底本验收；Finalization 须有 Owner 对该阶段的明确授权，不据此推导最终质量验收或发布许可。

## 正文范围

规范正文只保留文章内容。页码、页边界、分栏与分页痕迹、刊物刊头与栏眉、联系方式等属于底本载体
而不属于文章，一律不进入规范正文；`source_page`、`printed_page` 和页面类型属于对象证据，保留在
临时目录。

PDF 的字符、坐标、字体和页面对象是重建证据，不直接等同于正文结构。

---

## 基本概念

### 三层结果

| 层    | 含义                       | 是否正式文本 |
| ---- | ------------------------ | ------ |
| 对象证据 | PDF 中实际字符、坐标、字体和页面对象     | 否      |
| 顺序文本 | 根据页面阅读顺序排列后的候选文字         | 否      |
| 规范正文 | 去除版面噪声、恢复语义结构后的 Markdown | 是      |

必须区分：

* `source_page`：PDF 文件中的物理页序，从 `1` 开始；
* `printed_page`：页面实际印出的页码，没有或无法确定时留空；
* **阅读顺序**：正文栏、边栏、脚注、图注等页面对象的读取先后关系；
* **语义结构**：标题、段落、列表、引文、脚注、表格等内容之间的关系。

不得仅根据：

* 坐标相邻；
* 字号大小；
* 字体变化；
* PDF 内部对象顺序

直接推断正文结构。

## 角色

| 角色       | 职责                                     |
| -------- | -------------------------------------- |
| Operator | 判断 PDF 类型、登记底本、提取页面对象、恢复阅读顺序、整理正文、记录异常 |
| Reviewer | 直接对照渲染页面核验文字、顺序、结构和注释                  |
| Owner    | 确认范围、裁决异常与疑难、决定是否达到 `human_verified`   |

一个 Agent 在一个阶段只承担一个角色。

角色阶段完成后，写清交接信息并停止，不自行进入下一角色阶段。

---

## 项目工件

### 底本层

由任务明确本地底本位置、原文作品目录和临时目录：

```text
<本地底本目录>/<底本文件名>.pdf
```

数字原生 PDF 同样作为底本登记，不直接修改。

至少确认：

* 文件名；
* 文件页数；
* SHA-256。

底本文件名与 SHA-256 写入 `work.json` 的 `source_scan`；页数及核验页面范围保留在临时证据中。已有底本登记表时更新原登记表，不建立平行清单；其中的 `work_id` / `work_ids` 与 `work.json` 的 `work_id` 对应。

---

### 项目层

```text
<原文作品目录>/
  work.json
  <work-id>.md
  source-issues.json   # 仅存在待裁决疑难时建立
```

`work.json` 是数字化项目的唯一总记录，至少保存：

* `work_id`
* 标题
* 年份
* 底本版本
* 已核实的著录信息
* `text_status`
* 底本文件名
* 底本 SHA-256

同一状态不得在多个文件中重复维护。

旧项目无需为了符合当前模板补建空文件；重新开启实际工作时，只补充本轮需要的工件。

---

### 临时文件

临时证据统一放在：

```text
<临时目录>/
```

包括：

* 字符与坐标清单；
* 页面对象；
* 页面渲染图；
* 原始提取文本；
* 顺序文本；
* 表格或文本框提取结果；
* 比较结果；
* 临时核验记录。

临时文件：

* 不属于正式语料；
* 不视为已核验文本；
* 不覆盖底本；
* 默认不提交仓库。

---

## 状态

新项目只使用以下正文状态：

```text
pdf_text_extraction_unverified
             ↓
pdf_text_human_collated
             ↓
human_verified
```

| `text_status`                    | 含义                                | 写入者      |
| -------------------------------- | --------------------------------- | -------- |
| `pdf_text_extraction_unverified` | 已形成完整规范正文草稿，尚未逐页人工核验              | Operator |
| `pdf_text_human_collated`        | Reviewer 已逐页对照，但仍有疑难或尚未获 Owner 验收 | Reviewer |
| `human_verified`                 | 正文、结构、异常页和关键著录均已确认                | Owner    |

状态必须反映实际核验程度。

旧项目的状态名称不因与当前模板不同而批量改写。核验程度按实际工作判断，不仅凭状态名称推定；状态变更须有相应核验和验收依据。

以下情况均不能代替人工核验：

* PDF 可以复制文字；
* 提取工具运行成功；
* 字符数与页面看起来接近；
* 两个提取工具输出一致；
* PDF 可以全文搜索。

候选文本之间的差异只作核对线索，不直接判为提取、OCR 或底本错误。按页面渲染和页面对象核对后再决定是否修正；无法确认的内容写入 `source-issues.json`，不猜补。

---

## 交接

每次角色交接至少说明：

* 已处理的页码或范围；
* 修改的正式文件；
* 已转入扫描件流程的异常页；
* 尚未解决的问题；
* 下一角色应从哪里开始。

默认不提交 Git。

只有 Owner 明确要求时，才按实际阶段组织提交，例如：

* 建项；
* 重建草稿；
* 核验；
* 定稿。

## 流程

### 第 0 步 — Operator 判断处理路线

1. 找到底本，确认不存在相同 SHA-256 的重复文件。
2. 检查 PDF 页数、页面尺寸和文档属性。
3. 从正文、标题、脚注、表格和特殊字符页提取或复制文字。
4. 将提取结果与页面渲染逐字对照。
5. 确认项目归属、`work-id` 和输出位置。

只有同时满足以下条件，才继续本流程：

* 大多数正文字符能够稳定提取；
* 字符映射不存在系统性乱码；
* 正文没有大面积漏字；
* 页面对象足以恢复主要阅读顺序。

若整份 PDF 不满足条件，停止本流程并使用扫描件数字化流程。

若只有少数异常页：

1. 继续使用本流程处理可靠页面；
2. 登记异常 `source_page`；
3. 将异常页单独路由到扫描件数字化流程；
4. 最终将核验后的异常页文本合回正文。

建立或更新 `work.json` 后停止。

---

### 第 1 步 — Operator 建立页面与对象清单

按 `source_page` 顺序检查全部页面。

确定：

* 物理页序；
* 印刷页码；
* 页面类型；
* 单栏、多栏、边栏、脚注区、图注区；
* 文本对象；
* 嵌入图像；
* 矢量图形；
* 表格；
* 字体与字号；
* 字符映射；
* 异常字形；
* 页面旋转；
* 裁切框；
* 隐藏文字；
* 重复文字层。

可根据证据需要使用不同工具，例如：

* 字符与坐标提取；
* 页面对象分析；
* 表格或文本框交叉核对；
* PDF 内部结构检查。

工具服从证据需要，不为一次性检查增加长期维护脚本。

页面清单、`source_page` 与 `printed_page` 的对应关系、页面类型和异常页路由记录保留在临时目录，
不建立正式的页序文件，也不写入规范正文。

完成后进入第 2 步。

---

### 第 2 步 — Operator 提取顺序文本

先保存页面级对象证据，再恢复阅读顺序。

不得一开始就把整份 PDF 直接压成一个连续文本文件。

处理时：

* 保留文字来自哪个 `source_page`；
* 多栏页面按实际阅读顺序排列；
* 脚注与对应正文保持关联；
* 图注、表题和边栏按实际语义位置处理；
* 页眉、页脚、印刷页码、刊头和栏眉识别为版面对象，不混入正文；
* 重复文字层只保留实际可见且正确的一份；
* 页末连字符是否合并必须根据上下文确认；
* 无法映射的字形保留位置证据，不凭字形相似自行猜测。

Unicode 规范化只允许处理：

* 等价编码；
* 明显的组合字符问题；
* 纯排版造成的字符分裂。

不得静默：

* 现代化拼写；
* 改写原文；
* 改写标点；
* 翻译文字；
* 校正事实；
* 补全残句。

本步骤产出的是**顺序文本候选**，不是正式正文。

完成后进入第 3 步。

---

### 第 3 步 — Operator 重建规范正文

根据顺序文本和页面证据整理 `<work-id>.md`。

恢复：

* 标题及层级；
* 自然段；
* 列表；
* 引文；
* 脚注；
* 表格；
* 图题；
* 表题；
* 必要的图片位置说明。

删除纯版面噪声：

* 页眉和页脚；
* 印刷页码、页边界标记和分页痕迹；
* 运行标题和栏目栏眉；
* 刊物刊头、卷期号、ISSN 和出版商版面文字；
* 邮箱、通信地址和其他联系方式；
* 纯版面换行。

合并：

* 由物理分页拆开的句子；
* 经上下文确认的断词；
* PDF 对象切分造成的伪段落边界。

结构判断必须同时依据：

> 文字内容 + 页面渲染 + 页面对象

不得仅因为：

* 字号较大就判定为标题；
* 坐标相近就判定为同一段；
* PDF 对象连续就判定为同一句。

编辑者新增的标题、说明或补充必须明确标记，不得与原文混同。

本阶段只恢复作品原有的自然结构，不建立后续任务结构。

整理完成后检查：

* 正文首尾；
* 页面连接处；
* 标题层级；
* 脚注引用与定义；
* 多栏页面顺序；
* 表格与图注；
* 异常页占位与定位。

然后设置：

```text
text_status = pdf_text_extraction_unverified
```

停止，交 Reviewer。

---

### 第 4 步 — Reviewer 逐页核验

Reviewer 必须同时查看：

* PDF 渲染页面；
* 当前 Markdown 正文。

不得只比较不同提取工具的输出。

所有正文页必须逐页核验，不得抽样验收。

逐页检查：

1. 是否存在漏字、乱码、重复字或错误字符映射；
2. 是否错误合并或拆分连字符、单词和句子；
3. 人名、术语、数字、日期、公式和特殊字符是否正确；
4. 多栏阅读顺序是否正确；
5. 段落和标题边界是否正确；
6. 脚注、引文、图注和表格是否完整且归属正确；
7. 页眉、页脚、页码和隐藏文字是否误入正文；
8. 编辑性补充是否与原文区分；
9. 元数据是否来自底本或已核实来源，而不是文件名猜测。

#### 可以确定的问题

能够直接从页面确认的错误，Reviewer 直接修正正文。

#### 无法确定的问题

建立或更新：

```text
source-issues.json
```

每条至少包含 `id`、`source_quote`、`issue` 和 `handling`：

```json
{
  "issues": [
    {
      "id": "S-001",
      "source_quote": "<底本原文片段>",
      "issue": "<问题>",
      "handling": "<本次如何处理>"
    }
  ]
}
```

字段要求依 [`STRUCTURE.md`](../STRUCTURE.md)。

不得为了完成核验而猜测填补。

全部正文页核验完成后设置：

```text
text_status = pdf_text_human_collated
```

停止，交 Owner。

---

### 第 5 步 — Owner 裁决与验收

Owner 处理所有尚未解决的问题并完成最终验收。

检查：

* 底本身份正确；
* 底本 SHA-256 正确；
* 页面处理范围完整；
* 所有正文页已经 Reviewer 对照；
* 所有异常页已经按扫描件流程核验并正确合回正文；
* 文字和阅读顺序正确；
* 标题、段落、脚注、引文、表格和图注结构正确；
* 编辑性补充与原文明确区分；
* Markdown 符合项目结构；
* 正文、索引和登记位置正确；
* `source-issues.json` 中不存在无明确结论的未决问题。

Owner 可以：

* 接受现有文本；
* 裁决疑难；
* 指定具体页面退回 Operator 或 Reviewer。

已确定的底本缺字、缺注或排印错误无法恢复时，Owner 可明确接受保留原貌，在 `source-issues.json` 写明依据和处理结论，不补造内容。该结论不代替未完成的页面核验。

退回必须明确：

* `source_page`；
* 问题；
* 应重新执行的步骤。

不得使用“重新检查全文”等无法执行的笼统要求。

全部通过后设置：

```text
text_status = human_verified
```

正文重建完成。

---

### 第 6 步 — 可选：版式复刻

只有用户或 Owner 明确要求复刻原版时才执行。

本步骤独立于规范正文，不影响 `human_verified`。

版式复刻必须以已经 `human_verified` 的正文作为文字来源。

可以利用原 PDF 中的：

* 页面尺寸；
* 字体信息；
* 字号；
* 坐标；
* 栏数；
* 图像位置

辅助建立版式。

若原字体不能合法取得或不能稳定嵌入，应选择覆盖所需字符的替代字体。

不得：

* 为追求视觉相似修改已核验正文；
* 使用大量逐页负间距掩盖结构错误；
* 用隐藏文字制造可复制假象；
* 把整页转成图片冒充重建。

若需要大量逐页补丁，优先重新检查：

* 字体度量；
* 页面尺寸；
* 栏宽；
* 正文结构；
* 脚注结构。

至少验收：

* 页面顺序；
* 页面尺寸；
* 文本溢出或截断；
* 遮挡；
* 缺字形；
* 错误字体回退；
* 脚注、图像和表格位置；
* 关键页与高风险页的视觉对照。

---

## 异常页路由

出现以下情况时，不再信任该页文字层：

* 大量 `U+FFFD`；
* 系统性乱码；
* 字形没有可恢复的 Unicode；
* 可见文字与隐藏文字层不一致；
* 公式、表格或特殊字符提取后无法辨认；
* 页面阅读顺序无法从对象可靠恢复；
* 大面积漏字或重复字。

对异常页：

1. 登记 `source_page` 和异常类型；
2. 渲染为足够清晰的页面图像；
3. 按 [`SCAN_DIGITIZATION_WORKFLOW.md`](SCAN_DIGITIZATION_WORKFLOW.md) 的页面转录与人工核验原则处理；
4. 将核验结果合回主 Markdown；
5. 在角色交接中列明经过视觉转录的页面。

不要因为少数异常页而对整份可靠 PDF 重新 OCR。

也不要为了坚持数字原生路线而保留已经证明错误的文字层。

---

## 完成条件

数字原生 PDF 重建只有同时满足以下条件才算完成：

* 底本已经登记；
* 底本 SHA-256 可核对；
* 所有正文页都有可追溯的对象提取或视觉转录依据；
* 所有异常页已经完成相应视觉核验；
* 所有正文页已经 Reviewer 对照 PDF 渲染页；
* 正文文字已经确认；
* 阅读顺序已经确认；
* 标题、段落、注释、引文、表格和图注等语义结构已经确认；
* 所有疑难已经解决，或以明确页面、内容和理由保留；
* Markdown 正文符合项目结构；
* 必要索引和登记表已经同步；
* `work.json` 的 `text_status` 为 `human_verified`，且与实际核验程度一致。

以下情况均不能单独作为完成依据：

* 提取工具运行成功；
* 两个工具输出一致；
* 字符数接近；
* PDF 可以全文搜索；
* 文字可以复制；
* Markdown 阅读流畅；
* 版式复刻与原 PDF 视觉相似。
