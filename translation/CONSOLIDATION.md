# 统稿规范

本文件只适用于**全书统稿阶段**。

全书各批次 `status` 均为 `translated` 后，进入本流程。统稿按本规范默认执行建分支、提交与合并。这些 Git 操作在任务指定的翻译项目仓库中进行。

从 `main` 创建统稿分支：

```text
consolidation/<作品>
```

全部统稿工作在该分支完成。创建分支后，先将 `review-notes.json` 的 `source` 填为统稿分支起点的 commit hash，作为全书翻译完成、统稿开始前的基线。

---

## 扫描与判定规则

清点、落实后的复扫以及最终核对均遵守以下规则。

- **机械扫描用于发现候选，错误由语义判定确认。**
- **原文侧与译文侧交叉核对。**原文侧用于定位术语及其词形、固定形式和实际语境；译文侧用于发现旧译、非规范译法和跨单元漂移。完整范围由两侧结果共同确定。
- **词形匹配使用词界或等价的词法边界。**
- **按实际 occurrence 逐处判定。**同一 `block_id` 内的每个 occurrence 分别判定。
- **对机械扫描无法可靠覆盖的情况进行针对性语义补查。**包括插入修饰语、回指、多义、同形异义及其他句法变体。
- glossary 的 `forms` 只记录词形和固定形式。
- 术语一致的结论以语义核对为准；机械检查和旧译检索提供候选。

---

## 第 1 步 — 清点

建立本轮统稿需要处理的完整问题集。

`review-notes.json` 是**译文层问题**在统稿阶段的唯一工作清单。

1. 取 `review-notes.json` 中 `checked` 为空的已有条目。
2. 按 `glossary/` 中 `approved` 条目及已裁决的作品约定对全书进行一致性核对；多个词条可能适用时依 `GLOSSARY_RULES.md`「多个 approved 条目的适用判断」。
3. 检查各批次 `<batch_id>-reports.md` 中明确留待统稿处理的问题。
4. 对机械扫描结果进行语义甄别；确认属于译文问题且尚未登记的，补入 `review-notes.json`。
5. 将待处理条目按实际问题归类。同一术语、体例、专名、记号或其他同源问题可作为一类处理。

条目格式与登记粒度依 `REVIEW_NOTES.md`。

只为确有待处理或待裁决问题的单元建条目，已确认正确的对照位置写入相关条目的 `comment`。正常语境变体按成立处理。

glossary 自身的问题直接在 `glossary/` 处理，例如：

- `zh_preferred`、`zh_alternatives` 或 `notes` 的权威问题；
- `forms` 缺漏或错误；
- glossary 条目自身的结构问题。

glossary 问题已经造成具体译文错误时，该译文 occurrence 登记为 review-note。

清点针对**全书视角下的一致性、术语、体例、结构及既有遗留问题**。统稿以清点确认的问题为修改范围，落实后的针对性复扫和最终复核属于本流程；逐句全文复审由 Owner 另行指定。

完成后进入第 2 步。

---

## 第 2 步 — 裁决

处理所有尚无明确解决方案的问题。

1. 汇总同类条目的实际原文、译文和必要上下文。
2. `solution` 为空或现有 `solution` 不足以执行时，停下等待 Owner 裁决；涉及术语时写明拟处理范围。
3. 裁决结果及其适用范围写入对应条目的 `solution`。
4. 涉及权威译法时，按 `glossary/GLOSSARY_RULES.md`「裁决范围」决定是否更新 glossary；条目状态依同一文件。

临时候选清单、扫描输出及核对材料存于任务指定的临时目录，只用于支持裁决；最终结论由：

- `review-notes.json` 的 `solution`；
- glossary 的权威字段

持久保存。

完成后进入第 3 步。

---

## 第 3 步 — 落实

按问题类落实已经确定的解决方案。

1. 同一类问题集中处理全书，不按单个条目或单元零散修改。
2. 修改前核对：
   - 对应原文；
   - `file`；
   - `block_id`；
   - `comment` 中登记的其他位置；
   - 全书中同类问题的实际范围。
3. 登记数量或位置与实际文本不一致时，以实际文本为准。
4. 问题范围超出原条目的 `block_id` 时，处理所有确认属于同类问题的 occurrence。
5. 修改完成后，按原清点标准重新扫描并逐处复核。
6. 将落实该类译文修改的 commit hash 写入相关条目的 `checked`。

若复核后确认某条无需修改：

- 保持译文不动；
- 在 `solution` 中明确写明现译成立；
- `checked` 绑定到完成该结论复核时的译文状态 commit。

语义正确的正常语境变体保持原样。

完成后进入第 4 步。

---

## 第 4 步 — 最终复核

对全书当前状态进行收口检查。

| 对象         | 检查内容                                                     |
| ------------ | ------------------------------------------------------------ |
| review-notes | 全部条目已有明确 `solution`，且 `checked` 非空               |
| 条目定位     | `file` 与 `block_id` 均可解析                                |
| 底本与译文   | 各单元 `block_id` 序列一一对应，无重复、缺失或逆序           |
| 脚注等结构   | 依 `TRANSLATION_STYLE.md` 的结构元素规则，底本与译文对应      |
| 批次状态     | 全部为 `translated`                                          |
| commit 绑定  | 各批次 `operator_commit`、`reviewer_commit` 完整且与既有事实一致 |
| glossary     | 本轮发现的权威、结构和明确译法漂移均已解决                   |

发现新的**译文层问题**时，回到第 1 步补登。

发现 glossary 自身问题时按 `GLOSSARY_RULES.md` 处理；涉及既有权威或裁决范围时回到第 2 步交 Owner。若因此产生具体译文问题，再回到第 1 步登记。

已经语义确认成立的 contextual candidate 按完成处理。

检查结果分别说明：

- **结构检查**：已检查的单元范围、block-id、脚注、图片路径及相关数据文件的结果；
- **语义核对**：已核对的术语、作品约定及跨单元关系的范围，含正文、书目、索引和重复引文的对应；
- **保留候选**：经语义判断成立的候选类别及必要的适用边界；
- **未完成项**：检查失败、跳过的范围和仍不确定的问题。

结果写入当次交接。未完成项处理后进入收尾。

---

## 第 5 步 — 收尾

1. 核对 `review-notes.json` 的 `source` 为**全书翻译完成、统稿开始前的基线 commit hash**。
2. 逐条确认本文件「完成条件」全部满足。
3. 将统稿分支合回 `main`，生成只负责合并的 `merge` 提交。
4. 合并完成并复核 `main` 后，删除统稿分支。
5. 停止统稿流程。

统稿完成表示本轮全书问题已按本流程处理和复核；原文数字化核验、成书排版验收和公开许可各有其流程。收尾后发现新的问题，在现有工件中新增后续处理，已闭环条目和批次状态保持原样。

---

## 边界

翻译与审校依 `TRANSLATION_WORKFLOW.md`。

review-note 的字段、登记范围和格式依 `REVIEW_NOTES.md`。

术语归属、权威和状态依 `glossary/GLOSSARY_RULES.md`。

统稿阶段以全书为单位处理清点确认的问题，逐句全文复审由 Owner 另行指定；结论保存在 `review-notes.json` 与 glossary；批次状态保持 `translated`。状态或 commit 字段与已有提交事实不一致时，依据明确提交证据进行事实性回填。

---

## 完成条件

以下条件全部满足时，统稿完成：

- `review-notes.json` 全部条目的 `checked` 非空；
- 统稿问题均已裁决；
- `source` 已绑定全书翻译完成时的基线 commit；
- 全书底本与译文结构检查通过；
- 全部批次为 `translated`；
- 全部批次必要 commit 字段完整；
- 本轮发现的 glossary 权威或结构问题全部解决；
- approved glossary 反向核对发现的**明确译法漂移**均已处理；
- 结构检查与语义核对分别报告实际覆盖范围，跳过项和未决问题均有说明并已处理；
- 第 4 步的最终复核全部通过；
- 统稿分支已合并回 `main` 并删除。
